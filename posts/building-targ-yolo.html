Notes from building TARG-YOLO

What starting from a strong baseline taught me about evaluation, branches, and repository hygiene.

20 March 2026 6 min read Research Engineering

The first version of TARG-YOLO was not a clever idea. It was a working copy of YOLOv9 that I could run from end to end. That sounds unambitious, but it was the most important step in the project. Until the baseline trains, evaluates, and reproduces a number, every architectural change is a guess.

Start with a baseline you can trust

Reproducing a baseline is not glamorous. It is also the only way to know whether a change helped. We spent time on the data pipeline, augmentation, and evaluation protocol before touching the architecture. The goal was not to match the published number exactly; it was to have a stable reference point that we understood.

Three training entry points remain in the repository: train.py, train_dual.py, and train_triple.py. They reflect the multi-branch training style of the YOLOv9 codebase. Keeping them separate made it possible to compare configurations without rewriting the training loop. It also made the repository harder to read. A year later, I would add one page that says, plainly, which script to use and why.

Put new ideas in their own files

RepMS.py and DDetHead.py are deliberately small and self-contained. The rest of the repository is the baseline. This is not only aesthetic. When an experiment fails, separate files make it easier to remove the change and return to a known state.

The loss is the exception. TARG-IoU touches the training code and interacts with the data pipeline, so it cannot be isolated as cleanly as a module. That is a useful reminder: some ideas are architectural, and some are woven into the process. The second kind is harder to evaluate and harder to remove.

Evaluate like you expect to be wrong

Small-target detection is full of ways to accidentally flatter a model. Crop the evaluation images and the target becomes larger. Tune the confidence threshold on the test set and the mAP becomes a souvenir. Compare against a baseline trained with different augmentation and the improvement may be an artifact.

We tried to keep the protocol fixed: same data, same splits, same augmentation budget, same evaluation script. The comparisons in the paper are against YOLOv9 and YOLOv12 under the reported settings. Even then, a single number is a summary, not a proof.

The unglamorous lessons

Checkpoints do not belong in Git. The repository carries a 103 MB yolov9-c.pt and a runs/ directory. It works, but it makes cloning slow and buries the code. If I rebuilt the repository, weights would be release assets and runs would be ignored.

Log the command, not just the result. A run is a configuration plus a seed plus a machine. If you cannot reconstruct it, you cannot debug it.

Keep a failing example. One image where the model misses a target is worth more than ten aggregate plots. It gives you a place to start asking why.

Write the README first. A reader who cannot run your code in ten minutes will not stay for the architecture diagram. Write it before the paper, not after.

Separate “works” from “better.” A module can improve one metric and hurt another. Decide what you are optimizing before you celebrate.

The baseline gives you a head start. Discipline is what turns the head start into a result you can defend.

What I would do differently

Build a small, boring evaluation harness first. Add one change at a time. Keep a table of every run, the exact commit, and the command. Write the explanation for a reader who has ten minutes, not a reviewer who has ten pages.

I would also separate the research repository from the paper artifact. The research repository can be messy and fast; the artifact should be minimal, documented, and tested. Trying to make one repository do both jobs is how you end up with a 100 MB checkpoint next to the source code.

The code is public

If you reproduce the work, I would genuinely like to hear what breaks. Negative results are welcome. So are questions that start with “why did you…?” — those are usually the ones worth answering.

Repository. The implementation is at github.com/hkhldzf/TARG-YOLO. The paper is at doi.org/10.1007/s00138-026-01792-2.
